01Purpose & Scope

This document defines every integration point between the Vendor Registration Portal (VRP) and internal or third-party systems: the interface style, data contract, security, volumes, and failure behaviour. It is the authoritative reference for build, test and operational support of cross-system data exchange.

It covers identity, master data, ERP, qualification services (tax, sanctions, credit, banking), document storage, notifications, and analytics. It does not redefine functional behaviour (see FRD) or internal application architecture (see TRD).

Integrations are mediated by an Integration Layer (iPaaS / ESB) and exposed/consumed through an API Gateway. No point-to-point connections between the VRP application and external endpoints are permitted (see §3).

03Integration Principles

IDPrincipleStatement
IP-01Mediated, not point-to-pointAll external traffic traverses the API Gateway and Integration Layer; the application holds no third-party credentials directly.
IP-02API-first & contract-firstEvery synchronous interface is defined by an OpenAPI 3.1 contract; every async event by a published JSON Schema, versioned and stored in the contract registry.
IP-03Event-driven where possibleState changes are emitted as events; consumers subscribe rather than poll.
IP-04IdempotencyAll write operations accept an idempotency key; replays must not create duplicates.
IP-05Loose coupling & versioningBackward-compatible changes only within a major version; breaking changes require a new versioned endpoint and a deprecation window of 6 months.
IP-06Security by defaultmTLS + OAuth 2.0 client credentials between services; least-privilege scopes; no PII in URLs or logs.
IP-07ObservabilityEvery call carries a W3C traceparent; correlation IDs propagate end-to-end.

05Interface Specifications

5.1INT-01 · Identity Provider (OIDC / SCIM)

Purpose
Authenticate internal users via SSO; provision/de-provision internal accounts and roles.
Protocol
OpenID Connect (Authorization Code + PKCE); SCIM 2.0 for provisioning.
Auth
Client secret + PKCE; JWKS-validated ID tokens.
Data
sub, email, name, groups → mapped to VRP roles.
Frequency
Interactive (login); SCIM near-real-time on HR changes.
IDRequirement
INT-01-R1VRP shall accept only RS256-signed ID tokens validated against the IdP JWKS endpoint, with clock skew tolerance ≤ 60 s.
INT-01-R2Group-to-role mapping shall be configurable; an unmapped group results in no access (deny by default).
INT-01-R3SCIM deactivation shall revoke active sessions within 5 minutes.

5.2INT-04 · ERP Vendor Master Publish

Purpose
Create/update the vendor master record in ERP on approval and on subsequent approved changes.
Protocol
REST POST /vendors (preferred) or iDoc CREMAS via the Integration Layer.
Pattern
Synchronous command for ID confirmation; async event for status changes (suspend/inactivate).
Idempotency
Header Idempotency-Key = VRP registration UUID.

Sample Request

// POST /erp/v1/vendors  — INT-04
{
  "idempotencyKey": "f1c2-9a8b-4d3e",
  "vrpRegistrationId": "VRP-2026-018734",
  "legalName": "Acme Components Pvt Ltd",
  "taxId": "27AABCA1234F1Z5",
  "country": "IN",
  "category": ["31160000", "40140000"],
  "addresses": [{ "type": "REGISTERED", "line1": "...", "city": "Pune", "postal": "411001" }],
  "banking": [{ "currency": "INR", "iban": null, "accountNo": "****4821", "ifsc": "HDFC0000123" }],
  "riskTier": "LOW"
}

Sample Response

{
  "erpVendorId": "0001045892",
  "status": "CREATED",
  "createdAt": "2026-06-24T09:14:22Z"
}
IDRequirement
INT-04-R1VRP shall not mark a registration ACTIVE until ERP returns CREATED with an erpVendorId.
INT-04-R2On a 5xx or timeout, VRP shall retry with exponential backoff (max 5 attempts) preserving the idempotency key, then move to PUBLISH_FAILED.
INT-04-R3Banking fields shall be transmitted in full only over the mediated, encrypted channel; portal logs shall mask all but the last 4 digits.

5.3INT-03 · Sanctions & PEP Screening (Async)

Purpose
Screen the organisation, officers and UBOs against sanctions/watchlist/PEP datasets.
Pattern
Submit screening request → provider processes → webhook callback with results.
Callback
Signed webhook (HMAC-SHA256) to /webhooks/screening.
SLA
P95 result within 60 s; periodic re-screen every 30 days (batch).
// Webhook payload — INT-03 callback
{
  "requestId": "scr_8842",
  "vrpRegistrationId": "VRP-2026-018734",
  "decision": "REVIEW",          // CLEAR | REVIEW | HIT
  "matches": [
    { "entity": "officer:J. Doe", "list": "OFAC-SDN", "score": 0.82 }
  ]
}
IDRequirement
INT-03-R1A HIT or REVIEW decision shall move the record to ON_HOLD and create a Compliance task (FRD BR-004).
INT-03-R2Webhook signatures shall be verified; unsigned or invalid callbacks are rejected and alerted.
INT-03-R3If no callback is received within 10 minutes, VRP shall poll the status endpoint as a fallback.

07Integration Security

IDControlRequirement
SEC-INT-01TransportTLS 1.2+ for all external calls; mutual TLS between internal services.
SEC-INT-02AuthenticationOAuth 2.0 client-credentials with short-lived tokens; secrets in a managed vault, rotated ≤ 90 days.
SEC-INT-03AuthorizationPer-interface scopes; least privilege; deny by default.
SEC-INT-04Webhook integrityHMAC-SHA256 signature + timestamp + nonce; reject replays older than 5 min.
SEC-INT-05Data protectionPII/banking encrypted in transit and at rest; field masking in logs and traces.
SEC-INT-06Rate limitingPer-client quotas at the gateway; 429 with Retry-After on breach.
SEC-INT-07Allow-listingExternal callbacks accepted only from published provider IP ranges.

08Error Handling & Resilience

IDConcernRequirement
RES-01RetriesTransient failures (timeout, 5xx, 429) retried with exponential backoff + jitter; max attempts per interface as configured.
RES-02IdempotencyRetried writes reuse the idempotency key to prevent duplicate side effects.
RES-03Circuit breakerA provider exceeding the error/latency threshold is short-circuited; the portal degrades gracefully (queues work) rather than failing the journey.
RES-04Dead-letter queueUnprocessable async messages move to a DLQ with full context for manual replay.
RES-05CompensationIf ERP create succeeds but a later step fails, a compensating event reconciles or flags the inconsistency.
RES-06Standard error shapeAll synchronous errors use RFC 9457 application/problem+json with a stable type and correlation ID.
 
// RFC 9457 problem+json
{
  "type": "https://vrp/errors/erp-unavailable",
  "title": "ERP temporarily unavailable",
  "status": 503,
  "correlationId": "c-7f3a91",
  "retryable": true
}
