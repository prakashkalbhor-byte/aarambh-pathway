01Purpose & Scope

This document specifies the technical design and constraints for building, deploying and operating the Vendor Registration Portal (VRP). It is the engineering authority for architecture, stack, data, security and infrastructure decisions, and supports the functional behaviour in the FRD and the interfaces in the IRD.

02Architecture Overview

The VRP follows a modular, service-oriented architecture: a single-page front end, a backend-for-frontend (BFF) gateway, and a set of bounded-context services communicating synchronously (REST) and asynchronously (events). External systems are reached only through the Integration Layer (see IRD).

ClientSPA (vendor + internal consoles), responsive, WCAG 2.2 AA.
EdgeCDN, WAF, API Gateway — TLS termination, routing, rate limiting, authn.
BFFAggregates services for the SPA; session, CSRF, request shaping.
Domain ServicesRegistration · Workflow · Qualification · Document · Notification · Admin/Config · Audit.
EventingDurable message broker — domain events, async screening, DLQ.
DataRelational DB (per service), object store (documents), cache, search index.
IntegrationiPaaS/ESB connectors to IdP, ERP, MDM, screening, tax, banking, email.

4.2Data Management Requirements

IDTopicRequirement
DATA-01OwnershipEach service owns its schema; cross-service access is via API/events only — no shared tables.
DATA-02ClassificationBanking, tax and UBO data classified Restricted; encrypted at rest with envelope keys in a managed KMS.
DATA-03ResidencyRestricted data stored in-region per data-residency rules; storage region is configurable per tenant/country.
DATA-04RetentionSubmission artefacts 10 years; audit 7 years; soft-delete then purge per policy.
DATA-05PII minimisationOnly fields with a documented purpose are collected; subject-rights export/erasure supported.
DATA-06Audit immutabilityAudit log is append-only and tamper-evident (hash-chained); no update/delete API.
DATA-07BackupsAutomated encrypted backups; PITR enabled; restores tested quarterly.

05API Design Standards

IDRequirement
API-01REST resources are noun-based, plural, versioned in the path (/api/v1/...); JSON request/response.
API-02Every endpoint is defined contract-first in OpenAPI 3.1 and published to the developer portal.
API-03Errors use RFC 9457 problem+json with stable error types and a correlation ID.
API-04Writes accept an Idempotency-Key; pagination is cursor-based; filtering/sorting via query params.
API-05All requests authenticated (OAuth 2.0 / OIDC); fine-grained authorization enforced server-side per resource.
API-06Backward-compatible evolution only within a major version; deprecations announced with a 6-month window.

06Security Architecture

IDDomainRequirement
TSEC-01EncryptionTLS 1.2+ in transit; AES-256 at rest; keys in managed KMS/HSM, rotated ≤ 90 days.
TSEC-02AuthNOIDC for staff (MFA enforced); CIAM with MFA option for vendors; no shared accounts.
TSEC-03AuthZRBAC with attribute conditions (country, category); field-level access for Restricted data; deny by default.
TSEC-04SecretsNo secrets in code or images; injected from a vault at runtime; automatic rotation.
TSEC-05Input safetyServer-side validation, output encoding, parameterised queries; CSP, HSTS, anti-CSRF tokens.
TSEC-06App securityAligned to OWASP ASVS L2; SAST, DAST, dependency and container scanning in CI; annual pen test.
TSEC-07LoggingSecurity events centralised to SIEM; PII/banking masked; tamper-evident.
TSEC-08Segregation of dutiesSOX controls: no single identity can both create and approve a vendor; enforced in Workflow.
TSEC-09Tenancy isolationNetwork segmentation between tiers; private subnets for data; egress allow-listed.

11Quality, CI/CD & Constraints

11.1Engineering Quality

IDRequirement
QA-01Unit + integration test coverage ≥ 80% on changed code; quality gate blocks merges below threshold.
QA-02Consumer-driven contract tests for every interface (see IRD §10) run in CI.
QA-03Automated accessibility checks (axe) and Lighthouse budgets in the pipeline.
QA-04SAST, DAST, SCA and container image scanning gate every release; criticals block.
QA-05Performance/load tests run before each major release against UAT.

11.2Constraints & Standards

  • All code in version control; trunk-based or short-lived branches with mandatory peer review.
  • Browser support: latest 2 versions of Chrome, Edge, Firefox, Safari; no IE.
  • Compliance alignment: GDPR, CCPA, SOX; OWASP ASVS L2; WCAG 2.2 AA.
  • Infrastructure and application changes follow the organisation's change-management process.
  • Third-party libraries must have an approved licence and no known critical CVEs at release.
